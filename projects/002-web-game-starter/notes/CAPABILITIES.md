# web-starter-kit：基础展示与播放，核心仍在资产

依据本地固定版本 `d5f62cb074b506697fb035c420415026bafbe792` 的 README 与实现核对，日期 2026-09-15。下面区分原库实现、已演示范围和本项目新增内容；没有把依赖包的全部功能视为库已完成的功能。

## 研究结论

**对我们当前的“精致人物 + 舞蹈表现 + 内容创作工具”目标，这个库参考价值有限，不作为核心技术方向继续投入。核心仍在高质量 3D 人物与舞蹈动作资产，以及资产适配和编辑体验。**

它主要提供基础 3D 展示、已有模型接入与已有舞蹈动作播放。实际人物模型和动作仍需要自己制作，或购买、委托制作、取得授权素材后适配。演示自带的模型与动作是样例资产，不等于库具备通用人物生成、舞蹈生成或编辑能力。

此前用“可以承载展厅、导览、小游戏”等潜在用途来描述它，容易高估它已经完成的工作。这些用途仍要投入资产、规则和产品开发；可作为开发起点，不代表显著节省我们的核心成本。

阅读顺序：**人物 / 动作资产 → 格式与骨架适配 → 库接入和播放 → 浏览器展示**。Three.js / WebGL 等提供底层能力。人物造型、贴图、服装、骨骼与蒙皮影响人物质量；编舞、动作数据、节奏与修整影响舞蹈质量；灯光、渲染和适配也会影响最终效果。

| 问题 | 我们的判断 |
| --- | --- |
| 能否接入人物并播放舞蹈？ | 可以，这是当前最直接的基础能力。 |
| 能否帮我们制作精致人物与丰富舞蹈？ | 没有现成生成器或完整制作工具，仍需另外制作或取得资产。 |
| 是否没有任何额外代码价值？ | 不是。资源压缩、加载、阴影、声音等工程模块可以按需参考。 |
| 是否显著减少我们当前的主要工作？ | 没有证据支持；资产与创作编辑能力仍需开发，接入现有项目还会产生理解与适配成本。 |
| 是否继续围绕这个库投入？ | 当前不作为重点，保留示例与研究记录，遇到具体工程问题时再参考。 |

## 技术定位与事实边界

这是一套可以继续开发的浏览器 3D 游戏基础工程。它组合渲染、角色动画、物理、声音、界面、资源处理与开发规范，帮助开发者把三维素材做成可交互的软件。

Three.js 提供绘制三维世界的基础；这个项目在其上完成模块组合与工程处理。场景精美程度仍依赖模型、贴图、动作、灯光和制作质量。它本身不提供一键生成精致人物、舞蹈或音乐的模型服务，也不是可直接拖拽建场景的完整编辑器。

## 技术能力清单（保留事实，不等同于核心价值）

| 原库能力 | 技术原理 | 对 3D 场景的实际意义 | 当前证据与边界 |
| --- | --- | --- | --- |
| 场景组合与交互 | React Three Fiber 把 Three.js 对象组织成组件，场景组合角色、灯光、UI 与事件 | 点击按钮可触发人物、声音与特效；可发展为互动展厅、虚拟导览或小游戏 | 主场景已操作验证；业务任务需自行编写 |
| 已有角色与动作接入 | 带蒙皮的模型由动画轨道驱动骨骼，FBX 在构建时转为 GLB | 同一人物可播放待机、问候、舞蹈等动作 | 已验证 Tany / Mixamo 动作；不是任意模型与任意动作都无需适配 |
| 动作调整工具 | 两骨骼逆运动学、骨骼叠加层、朝向与脚步相关数学工具 | 可在动画上添加看向目标、手脚接触目标等局部调整 | 有源码与部分测试；仍需按人物骨架接线、调参；不是自动编舞 |
| 布娃娃与碰撞 | Rapier 刚体、肢体碰撞形状、关节约束，结果回写骨骼 | 跌落、被推倒、碰撞后的姿势由物理实时计算 | 布娃娃实验已验证；物理合理性不等于工程仿真精度 |
| 大面积地面 | 着色器扰动采样位置、旋转叠层、色调变化与随机采样 | 一张较小贴图铺较大地面时，减轻规则重复感 | 有实验；当前低对比度素材部分效果较细微 |
| 地形材质混合 | 在同一网格上按遮罩与高度信息混合土壤、道路、石块，采样显式梯度 | 场景地面更自然，减少材质交界处糊成一片的感觉 | 有实验；石块视差效果不自动产生真实碰撞几何，也不是地形雕刻编辑器 |
| 独立特效层 | 先绘制世界，再对独立特效场景做辉光、色调映射与合成；世界深度用于遮挡 | 可让魔法、舞台粒子发光，同时让墙和道具正确挡住特效 | 有实际渲染实现和主场景效果；特效形态仍需制作 |
| 资源自动处理 | Vite 插件压缩模型贴图/几何/动画，转换 FBX，处理图片与音频，并使用缓存 | 开发时导入素材，发布时自动得到适合网页加载的文件 | 本次构建角色约 4.3 MB → 711 KB；仅是这个素材的结果，不保证相同比例 |
| 启动加载与就绪管理 | 扫描导入关系生成资源清单、按字节显示进度；资源与场景就绪分两阶段检查 | 降低人物先出现、贴图后补齐等启动问题，避免手工维护资源列表 | 有实现与运行验证；大量素材仍需设计按需加载策略 |
| 重复物件与阴影优化 | 共享几何/材质、实例化；静态物体阴影缓存，动态投影单独更新或降频 | 对重复柱子、建筑、道具和少量移动人物，减少重复绘制工作 | 需按约定接入；缓存有适用条件和回退，未做大场景或手机真机压测 |
| 动态灯光预算 | 保留固定数量的特效灯，按优先级分配位置与亮度 | 避免每次闪光都增删灯光，引起材质着色器重新编译 | 固定数量也有常驻开销；灯池不提供阴影，不保证任意数量特效都便宜 |
| 游戏声音与设置 | Howler 混音、音乐/环境/音效/UI 分频道，播放池、播放列表与设置保存 | 音乐可以变小而环境声保持；按钮、碰撞和场景可使用不同声音 | 是播放与管理能力，不是音乐生成、语音对话或音频驱动编舞 |
| 响应式游戏 UI | React 控件、九宫格图像边框、按逻辑分辨率缩放 | 复用按钮、暂停菜单、音量面板，保持边框与布局 | 组件目录已验证；不是游戏逻辑或完整产品流程 |
| 固定步长模拟 | 模拟按固定时间间隔推进，画面通过插值跟随，隐藏/暂停时冻结 | 减少把规则速度直接绑定显示帧率的问题 | 布娃娃实验已使用；不自动保证跨设备物理完全确定 |
| 寻路基础 | Recast 从可行走网格生成导航网格，并建立 Crowd 对象 | 可以继续实现绕障碍移动、多个角色导航 | 有封装，但当前场景未接入完整寻路流程；庭院走的是预设路线 |
| 联网基础 | 同浏览器标签页 BroadcastChannel 通信、Photon 适配与实体状态同步抽象 | 可以继续开发多人同场景的状态同步 | 代码存在；云联网需 Photon 配置、玩法接入与验证，当前不算可玩的多人游戏 |
| 开发与检查流程 | 按功能拆分代码、独立实验页、技能与角色说明、测试和真实浏览器检查要求 | 扩展时能单独定位角色、物理、UI 等问题，给编码 Agent 明确工作规范 | 技能是开发说明；提到 Blender、Tripo、Mixamo 不等于这些工具和服务已安装或接入 |

## 对一个 3D 场景项目意味着什么

以“访客点击展品，角色移动过去，讲解时配合动作、灯光、提示卡”为例：

1. 原库可提供场景组件、已有角色动画、声音管理、UI、资源优化与加载流程。
2. 展品模型、讲解内容、角色动作和场景美术仍要准备。
3. 点击目标、路线选择、到达判定、讲解开始/停止等业务规则仍要开发；完整寻路需要接入现有基础模块。
4. 如果要求角色自由对话，需要另外接入对话与语音能力；如果要求多人参观，需要联网接入和状态同步设计。

因此，它节省的是从素材到可交互场景之间的一部分工程工作。节省多少取决于项目是否需要这些模块，不能仅凭演示估算开发时间或性能收益。

## 潜在用途仍需额外开发

| 产品方向 | 现有基础 | 主要需要补齐 |
| --- | --- | --- |
| 角色与舞台创作工具 | 角色、动画、材质、灯光、UI、音乐播放 | 角色模板与参数、动作时间轴、素材导入规范、保存/加载、作品导出 |
| 互动展厅与导览 | 场景、角色、声音、交互 UI | 内容管理、导航、讲解流程、设备适配 |
| 轻量网页游戏 | 渲染、动画、物理、声音、界面、模拟基础 | 玩法、关卡、输入控制、进度存储与完整体验验证 |
| 多人互动空间 | 场景基础与网络适配代码 | 房间流程、玩家状态、断线恢复、权限、服务端规则及联网测试 |

这些潜在用途不是继续选用此库的充分理由。创作产品真正需要验证的是：**修改角色外观 → 选择并排列动作 → 调整舞台 → 保存作品 → 再次打开还原**。这个闭环需要额外开发，也可以基于其他 Three.js 工程实现。

后续重点放在人物资产制作质量、舞蹈动作资产制作与积累、骨架兼容及重定向、动作衔接与编辑体验。这个库的压缩、加载和运行模块保留为参考；是否借用由具体问题决定，不把框架整合当成资产生产能力。
