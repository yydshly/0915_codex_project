02 / HOW A FINDING EMERGES

它怎样知道，
应该从哪里找问题？

先理解输入能到哪里，再寻找“不该发生的状态”。
点击步骤，查看每一阶段的输入、动作与产物。

提示词规定研究方式

规则告诉模型“怎么查”。

关注边界长度、截断结构、分配与复制之间的不一致；优先寻找有内存破坏证据的问题。正常错误处理、单纯耗尽内存、测试脚本自身的问题，不能直接作为高质量发现。

工具反馈改变下一步

具体输入由模型探索。

输入被拒绝，就回看前置检查；只触发断言，就继续分析邻近路径；出现有效证据，再缩小输入、重复运行。这不是把整个仓库一次塞进模型，也没有保证覆盖全部路径。

03 / AN INTERACTIVE THOUGHT EXPERIMENT

只改变一个数量，
观察假设怎样变得可检验。

教学计算 · 非真实漏洞扫描

设想一个解析器：每项数据占 4 字节，却用只能保存 0–255 的长度值记录分配大小。拖动数量，看“实际需要”与“记录的长度”是否分离。真实程序还需确认类型转换、检查逻辑和可达路径。

输入中的数量字段60 项
1 项64 项：长度开始回绕90 项

这里用 8 位长度放大现象。它不是生产级补丁建议，也未执行 C/C++ 程序。

计算得到的观察
需要写入的字节240
回绕后记录的长度240
真正的流水线还要做什么？

生成真实格式的文件 → 调用目标程序 → 获取检测器输出 → 确认错误位于项目代码 → 在新环境独立复现。

运行得到的结果，应该怎样解释？

正常拒绝

返回格式错误

程序正确处理异常输入。继续寻找其他路径。

环境或资源问题

内存耗尽 / 启动失败

先排查实验环境，不能据此认定内存破坏漏洞。

候选证据

项目代码触发 ASAN

保存输入和堆栈，交给独立验证者复现。

复现成立

新环境重复触发

问题证据更强；真实攻击影响仍需单独分析。

04 / VERIFY THE EVIDENCE, THEN THE FIX

发现者与验证者，
使用两个独立环境。

避免“只在发现者修改过的程序里成立”。
环境独立，也不意味着模型结论永远正确。

容器 A / 发现者

探索与实验

读取源码、尝试输入、运行程序。

产物：PoC + 复现信息
传递输入与必要元数据 →不继承修改后的源码、程序
或完整推理过程
容器 B / 独立验证者

从原始镜像重新开始

运行 PoC，检查真实输出。

产物：判断 + 执行证据
Grade 的五项要求
  1. 输入真实存在且非空
  2. 三次运行至少两次崩溃
  3. 排除内存耗尽与超时
  4. 堆栈指向项目代码
  5. 检查崩溃类型一致性

Find 要求提交前尽量达到 3/3；Grade 对部分可解释波动允许降分通过。综合结论由模型读取证据后生成，程序解析其判断。

JUDGE / 去重

这真是一个新问题吗？

流式模式下，模型串行对比已报告问题，判断新增、替换为更好样例或跳过重复；另有按 ASAN 签名聚类的命令。

REPORT / 影响

能触发，实际影响多大？

结合入口、攻击者控制程度和限制写报告，再独立评分证据。崩溃不自动等于远程代码执行。

TRIAGE / 优先级

多轮结果先处理哪个？

交互式分诊跨轮次合并同根因发现，根据环境前提调整严重性，标注组件归属。

补丁需要逐层通过验收

层级谁来判断实际检查仍然不能证明什么
T0 · 构建程序检查补丁可应用，构建退出成功业务逻辑一定正确
T1 · 原输入程序检查退出码 0，输出没有 ASAN 标记其他输入也不会出错
T2 · 回归程序检查现有测试通过；未配置则跳过未覆盖的行为没有回归
再次攻击模型探索新智能体尝试变体，默认 50 轮根因已彻底消失
T3 · 风格模型建议可选评分，不影响验收通过维护者一定接受补丁
一个容易忽略的实现边界：没有提交 PoC，不等于研究已充分完成

所读版本的再次攻击流程在 run_find 没有返回崩溃产物时，将其记为 clean，并未在这里单独检查智能体错误状态。复核时还应查看执行记录，区分“搜索完成且未发现问题”和“任务中断、没有产物”。这也是不能把再次攻击通过当作安全证明的原因。

对应实现 ↗

动态补丁阶段运行现有测试，不自动为每个漏洞添加永久回归测试。静态 /patch 在存在合适测试结构时会尝试生成测试，但仍需执行验证。

05 / FOUR DEPTHS OF CUSTOMIZATION

先判断你要改变什么，
再决定改到哪一层。

只想让它更懂你的项目，与让它检测一类新问题，
所需的改动量完全不同。

01 / 审查口径改指令

关注新的模块或组织规则

已有静态审查就够用，只需补充攻击入口、权限边界、重点类别与误报排除理由。

/vuln-scan ./src --extra .claude/scan-extras.txt
/triage ./VULN-FINDINGS.json --fp-rules .claude/fp-rules.txt
适用于交互式技能。这些参数不是动态流水线的通用检测插件。
02 / 同类新目标配目标

接入另一个 C/C++ 解析器

保持“文件输入 + ASAN 检测”的约定，提供构建环境、配置和薄入口封装，通常无需修改调度代码。

targets/my-parser/
├─ Dockerfile 源码 + 带检测器的程序
├─ config.yaml 路径、构建、测试与范围
└─ entry.c 读取输入并调用真实解析入口
入口必须覆盖你实际关心的生产路径；未调用到的代码不会自动获得覆盖。
03 / 新漏洞类别换判定标准

研究 Web 权限或业务状态问题

重新定义输入形式、失败信号、复现步骤、去重依据和修复标准；提示词、结果结构与验收代码要一起调整。

文件 + 崩溃 → 请求序列 + 权限断言
ASAN 无法判定越权，也不能把 HTTP 500 直接当作已证实的漏洞。
04 / 更换模型改运行层

保留流程，对接另一套智能体

适配模型调用、文件读写、命令执行、输出解析、会话恢复、凭据与网络配置。

Claude Code CLI → 模型适配器 + 工具循环
不是只替换模型名称；兼容接口也不能保证等同的发现能力。
定制的核心问题
“出现什么可观察的结果，
才算真的发现了我要找的问题？”

这个判定依据称为 oracle。它可以是内存检测报告，也可以是来自业务规范的断言。先把它定义清楚，模型才有可靠的实验反馈。

/customize 本身在做什么？

  1. 读现有实现识别 C/C++ 与 ASAN 假设
  2. 澄清目标输入、检测、环境、报告
  3. 列出改动确认具体迁移计划
  4. 修改并校准用已知问题的小目标验证

它是一份指导代码智能体修改框架的技能指令。运行 /customize 并不意味着所有语言和漏洞类别已经内置支持。

字段来自当前 TargetConfig。仓库地址与提交需替换为真实值，构建和测试命令需匹配目标；这份骨架未经运行，不能单独完成接入。

  - "解析长度字段：分配大小与后续写入是否一致"

07 / START WITH A SMALL, KNOWN TARGET

先证明检测链路有效，
再扩大搜索规模。

如果探测器看不见错误，增加智能体数量
只会放大没有证据的搜索。

1

准备一个可以重复启动的小目标

固定版本、依赖与初始数据。至少准备一个已知错误和一个正常输入，确认检测器能区分它们。新领域可制作包含少量预埋问题的 canary 校准目标，答案不交给发现者。

2

写清入口与判断标准

输入如何进入生产路径？什么权限可到达？哪个断言失败才算问题？业务需求需有独立依据，不能让模型仅从当前代码推导正确行为。

3

先跑一轮，检查完整产物

查看实际输入、命令、检测输出和新环境复现。运行失败、未覆盖与确认无问题要分别记录。只有报告文字、没有执行证据，还不能完成动态验证。

4

用结果校准，再考虑并行和修复

统计已知问题是否找到、正常输入是否误报、重复发现数量、补丁回归、耗时与成本。调整搜索区域和验证器后再放大规模。

查看上游 C/C++ 运行入口与产物目录

下面是已有目标的用法参考，不会在本网页执行。需提前准备支持 Docker / gVisor 的 Linux 环境、Python 3.11+ 和 Claude 访问凭据；在 Windows 上应另行准备兼容环境。命令中的模型名称和结果路径需自行替换。

# 一次性安装与沙箱准备：在上游仓库内
python3 -m venv .venv
.venv/bin/pip install -e .
./scripts/setup_sandbox.sh

# 已有 drlibs 目标的一轮发现、验证与流式报告
bin/vp-sandboxed run drlibs --model MODEL_ID --runs 1 --stream --auto-focus

# 单独生成并验证补丁
bin/vp-sandboxed patch results/drlibs/TIMESTAMP/ --model MODEL_ID

配置 Claude 认证后再执行。新目标完成适配后，用其目录名称替换 drlibs。

results/<target>/<timestamp>/
├─ 运行记录、PoC 与 result.json
└─ reports/bug_NN/
　 ├─ report.json 影响分析与评分
　 ├─ patch.diff 候选修复
　 └─ patch_result.json 分层验收结果

布局会随单轮或多轮模式变化；多轮通常带 run_NNN/ 子目录。

可以带走的方法

模型负责探索，证据约束结论。
定制的重点，是让“对或错”可被观察。

这个框架对自动业务测试也有启发，但迁移时需要新的规范、断言和环境恢复机制。当前页面完成的是原理分析与教学展示。
