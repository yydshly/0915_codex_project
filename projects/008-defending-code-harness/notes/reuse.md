# 复用思路：其他模型与业务测试

**本页是基于源码的设计建议，不代表上游已经提供对应实现，也不代表本次已验证迁移效果。**

## 1. 最值得复用的五个思路

| 思路 | 为什么有用 | 可迁移场景 |
| --- | --- | --- |
| 先定义范围 | 说明哪些输入和前提真实成立，减少无关发现 | 安全审查、业务验收 |
| 让假设落到可运行输入 | 把“可能有问题”变为可检查的实验 | 接口测试、解析器测试 |
| 发现与验证分开 | 避免继承被改过的环境和先入结论 | 自动修复、数据质量检查 |
| 将验收拆成层级 | 明确失败步骤，减少仅凭模型自评通过 | 编译修复、功能修复 |
| 保存证据并限制循环 | 支持复核、恢复和成本控制 | 长任务与多轮搜索 |

## 2. 换成其他模型，需要替换什么

仅借鉴方法，可以整理提示词交给其他代码智能体。复用自动流水线至少需要以下适配：

| 适配项 | 当前实现 | 迁移要求 |
| --- | --- | --- |
| 模型调用 | Claude Code CLI | 对接目标 API 或智能体运行环境 |
| 工具循环 | CLI 提供文件读写、命令执行 | 实现工具请求、执行和结果回传 |
| 返回格式 | stream-json 消息和文本标签 | 转成框架需要的产物与状态 |
| 会话恢复 | Claude session ID、resume | 保存上下文或使用目标运行层的恢复能力 |
| 身份与网络 | Claude 服务相关配置 | 更新凭据注入、代理和出口允许列表 |
| 阶段提示 | 按当前模型与工具设计 | 测试预算、上下文限制、输出一致性 |
| 效果校准 | 当前参考提示与示例目标 | 在有已知答案的小目标上比较发现与误报 |

可考虑让调度器只提交任务、预算和工具权限；模型适配器负责工具操作和最终产物。容器、证据存储与验收逻辑尽量放在模型适配器之外。

**减少供应商耦合不能保证不同模型拥有相同发现能力。** 推理、工具使用和上下文处理差异会影响结果。

## 3. 用于业务测试，需要增加什么

安全研究试图证明某个不该发生的行为能够发生。业务测试还要明确正确行为，覆盖正常、边界和异常流程。

| 要素 | 默认内存漏洞流水线 | 迁移到业务测试 |
| --- | --- | --- |
| 上下文 | 源码、入口、信任边界 | 需求、业务规则、权限与状态约束 |
| 测试产物 | 崩溃文件及命令 | 请求序列、数据、操作步骤和断言 |
| 判定信号 | ASAN 诊断、进程状态 | 响应内容、数据库状态、权限结果 |
| 独立验证 | 新容器重放输入 | 重置数据、时间和外部依赖后重放 |
| 修复验收 | 原崩溃消失、现有测试通过 | 新断言通过，其他业务行为保持正确 |

### 示例：一次性优惠券能否重复使用

以下为建议流程，不是仓库内置能力：

1. 明确需求：同一用户对同一张一次性优惠券最多核销一次。
2. 模型阅读领取、下单和核销代码，寻找重复提交或并发路径。
3. 生成重复或并发请求，准备独立测试账号和优惠券。
4. 运行请求，检查订单与核销记录。
5. 根据需求断言成功核销次数最多为一次。
6. 在重置数据的环境独立重放。
7. 如生成修复，将用例保留为回归测试，并验证正常结算。

需求和断言必须有独立依据。如果模型只根据当前代码推导预期结果，可能把现有错误当成正确规范。

## 4. 后续实验建议

选择可独立运行、规模小、存在已知错误且有正常测试的目标：

1. 固定源码和环境。
2. 确定一个漏洞类型或业务规则。
3. 验证“输入 → 检测信号”可用。
4. 接入一个模型分析与生成输入。
5. 交给独立环境复核。
6. 保存命令、结果、模型版本、耗时和成本。
7. 再增加并行搜索、自动补丁和跨模型比较。

记录正确性、复现率、重复发现、补丁回归和成本，才能判断自动化收益。当前仅完成思路整理，未安排或执行这些实验。
